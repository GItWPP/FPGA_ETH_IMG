# 串口图像处理实现方案

日期：2026-10-21
状态：原始方案已获用户批准并完成实施。用户已确认串口支持 1.5 Mbps；实际代码、仿真、综合与上板结果见 README.md 和 doc/验证记录.md。

后续版本已经扩展尺寸上限至 1920×1080，保持原有分块架构；当前版本与完整图像验收见 doc/1080p扩展验证.md。本文件中的 320×240 上限属于原始方案阶段。

## 1. 实验目标和范围

用户已确认的数据流为：电脑发送图片 → FPGA 处理 → FPGA 串口回传 → 电脑显示。

第一版建议采用纯 PL Verilog 实现，电脑通过外接 USB 转 TTL 串口模块连接 FPGA。上位机完成图片解码、缩放、RGB565 转换、发送、回收和显示；FPGA 完成串口协议、数据检查和逐像素处理。无需 PS 软件、DDR、HDMI 或外接显示屏。

第一版处理模式建议包括：原图回传、灰度化、反色。用户尚未指定具体处理算法，上述模式属于方案建议。后续增加需要邻域数据的滤波或边缘检测时，再引入行缓存。

## 2. 已核实的硬件条件

依据本目录 AX7Z020B 开发板用户手册和 uart_img.xdc：

| 项目 | 配置 | 依据 |
| --- | --- | --- |
| FPGA | XC7Z020-2CLG400I | 手册第 6、9 页 |
| PL 时钟 | 50 MHz，U18 | 手册第 16 页；XDC 时钟周期 20 ns |
| 复位 | KEY1，M15，按下为低 | 手册第 37 页；XDC |
| FPGA 串口接收 | uart_rx_i，T11，J20 第 9 针 | XDC；手册第 38 页；IO_J20.png |
| FPGA 串口发送 | uart_tx_o，T10，J20 第 10 针 | XDC；手册第 38 页；IO_J20.png |
| 板载 USB 串口 | PS_MIO49 / PS_MIO48 | 手册第 29 页 |

接线：

| USB 转 TTL 模块 | 开发板 |
| --- | --- |
| TXD，3.3V 逻辑 | J20 第 9 针，T11，FPGA RX |
| RXD，3.3V 逻辑 | J20 第 10 针，T10，FPGA TX |
| GND | J20 第 1、37 或 38 针 |

开发板独立供电，串口模块的 VCC 不必连接。必须使用 3.3V TTL 信号；RS232 电平不能直接接入。现有 PL UART 方案不能直接通过板载 Mini USB 串口收发；若改用板载串口，需要另行设计 PS UART 与 PL 数据通路。

顶层端口保持为 sys_clk、sys_rst_n、uart_rx_i、uart_tx_o。内部统一采用 50 MHz 时钟；RX 经过两级同步，顶层复位采用异步拉低、同步释放。直接控制 BRAM 地址/使能的包解析、应答和会话寄存器使用同步复位，避免异步 RAM 控制警告。

## 3. 图像格式与传输性能

- UART 使用 8N1，无硬件流控。用户已确认串口支持 1.5 Mbps，默认采用 1_500_000 bps；保留参数化配置以便调试时降低波特率。
- 50 MHz / 1.5 Mbps = 33.333… 个时钟周期/位。TX/RX 使用分数计时器或相位累加器，在 33/34 周期之间调节位间隔；RX 仍在位中心采样。全部逻辑使用 50 MHz 时钟和计时使能，不生成普通逻辑分频时钟。单纯固定 33 周期会得到约 1.515 Mbps，本方案采用分数计时消除该平均误差。
- 默认图片尺寸建议为 128×128，可在上位机调整。第一版建议将最大尺寸限制为 320×240，便于控制串口等待时间。
- 传输格式固定为 RGB565：R[4:0]、G[5:0]、B[4:0] 拼成 16 位像素，先发低字节，再发高字节；从左到右、从上到下排列。
- DATA 每包最多携带 1024 字节像素数据，长度必须为偶数。START 指定宽、高、格式和处理模式；END 检查累计像素字节数是否等于 width×height×2。
- 上位机显示回传结果时，将 RGB565 展开成 RGB888。原图对比区域应同时提供 RGB565 量化后的参考图，避免把格式量化误差误判为 FPGA 错误。

理论传输时间仅计有效图像数据，8N1 每字节占 10 bit。第一版采用逐包等待回传，两方向时间相加；实际还包含协议和 USB 调度时间。

| 图片尺寸 | 单向有效数据 | 1.5 Mbps 单向传输 | 1.5 Mbps 一次往返 |
| --- | --- | --- | --- |
| 128×128 | 32768 字节 | 约 0.218 s | 约 0.437 s |
| 320×240 | 153600 字节 | 约 1.024 s | 约 2.048 s |

1.5 Mbps 在 8N1 下单方向理论有效载荷上限为 150000 字节/秒。逐包等待回传会把一张图片的收发时间相加；上表未包含协议字节和主机逐包响应延迟，实际上板测量后再给出实测速率。

定位为静态图片实验。FPGA 逐像素计算的时间远小于串口传输时间。

## 4. 系统结构和模块划分

```text
上位机：图片加载 → 缩放/RGB565 → 分包发送
                                  │
FPGA：UART RX → 包接收/CRC → 接收块缓存 → 图像控制/像素处理
                                                        │
       UART TX ← 应答打包/CRC ← 处理结果块缓存 ←───────────┘
          │
上位机：回包校验 → 拼接像素 → RGB565 解码 → 原图/结果显示
```

| 建议模块 | 职责 |
| --- | --- |
| uart_img_top.v | 顶层连线、参数传递和复位同步 |
| uart_rx.v | 8N1 接收，分数计时、起始位确认、位中心采样、停止位检查 |
| uart_tx.v | 8N1 发送，分数计时、字节 valid/ready 握手 |
| img_packet_rx.v | 包头搜索、字段/长度检查、CRC16、接收超时 |
| img_block_buffer.v | 接收及结果块缓存，采用可推断 BRAM 的同步 RAM |
| img_ctrl.v | START/DATA/END 会话、序号、累计长度、重复包处理 |
| img_pixel_proc.v | RGB565 原图、灰度、反色，输入输出均带握手 |
| img_packet_tx.v | 状态/结果应答组包及 CRC16 |

采用约 1 KiB 接收缓存和约 1 KiB 结果缓存，另加少量协议状态。实际 BRAM 分配数量以综合报告为准。完整图片在电脑端缓存；这些逐像素算法无需 FPGA 整帧缓存。

灰度建议使用 RGB565 通道扩展到 8 位后计算 Y=(77R+150G+29B)>>8，再打包为 RGB565 灰度像素；上位机参考模型采用完全一致的整数运算。反色对 RGB565 的各颜色位取反。

## 5. 协议和关键时序

统一包结构建议为：

| 字段 | 字节数 | 规则 |
| --- | --- | --- |
| MAGIC | 4 | 固定 55 AA 5A A5 |
| VERSION | 1 | 第一版为 1 |
| CMD | 1 | PING、START、DATA、END，以及对应应答 |
| TRANSFER_ID | 2 | 本次图像传输编号 |
| SEQ | 2 | 请求序号，应答回显 |
| LENGTH | 2 | PAYLOAD 字节数，最大 1024 |
| PAYLOAD | 可变 | 命令参数、图像块或处理结果 |
| CRC16 | 2 | CRC-16/CCITT-FALSE，poly=0x1021，init=0xFFFF，非反射，无最终异或 |

多字节整数和 CRC 字段均按低字节先发。CRC 覆盖 VERSION 至 PAYLOAD，不包含 MAGIC 和 CRC 字段。后续实现时冻结命令码、状态码及 START 参数布局，并在 RTL 与 Python 中使用同一协议文档。

关键行为：

1. 上位机发送 PING，确认协议版本和设备响应；随后 START 指定宽高、RGB565 和处理模式。
2. 上位机发送一个 DATA 包，等待相同 TRANSFER_ID/SEQ 的处理结果，校验通过后才发送下一包。每个 DATA 成功应答就是对应的结果块，不再额外发送独立成功 ACK。
3. FPGA 先收完整包并校验 CRC，再处理缓存内像素。处理后生成带 CRC 的结果包，发送完成后保留最近一次应答以处理重试。
4. 状态流程为 WAIT_START → RECEIVE_BLOCK → CHECK_PACKET → PROCESS_BLOCK → SEND_RESULT → RECEIVE_BLOCK；END 校验整帧长度后结束会话。具体 RTL 可将包解析与会话状态分开实现。
5. 超时后上位机重发同一请求；FPGA 对相同编号和序号的重试重发缓存应答，不重复累计像素。首版限定一次只有一个未完成请求，只需缓存最近一次请求的应答。
6. 非法模式、越界尺寸、奇数像素字节长度、乱序和超出整帧长度应被拒绝。CRC 错误、串口停止位错误和包中断不得进入像素处理；解析器超时后恢复包头搜索。可可靠识别请求时返回错误应答，否则由上位机超时重试。
7. 主机每包重试次数建议为 3 次；等待时间按波特率和包长计算并加入 USB 调度余量。失败后显示具体原因，重新开始一帧；复位中断后通过新的 START 恢复。

valid/ready 时序：仅在 valid && ready 时交付字节或像素；反压期间保持数据稳定。同步 RAM 的读取延迟在处理流水线和打包逻辑中显式处理，避免首像素丢失和末像素错位。

## 6. 目录与工具交付

保持用户现有目录分工：

```text
UART_IMG/
├─ doc/      硬件资料、实现方案、冻结后的协议与接线说明
├─ rtl/      Verilog 模块
├─ sim/      自检 testbench、仿真脚本和生成的波形
├─ tools/    Python 上位机、依赖说明、Vivado 建工程/综合脚本

```

上位机建议采用 Python + pyserial + Pillow + Tkinter，提供串口/波特率选择、图片打开、目标尺寸、模式选择、发送进度、接收预览、结果保存及错误信息。串口操作在工作线程执行，界面更新通过主线程队列完成。提供命令行收发/自测入口，便于排除图形界面问题。

Vivado 工程选择 xc7z020clg400-2，加入现有 XDC；采用可综合 RTL 和推断 RAM。首次验收使用 Vivado 2019.2；用户后续新建了 Vivado 2024.2 工程 project_uart/project_uart.xpr，当前构建使用该独立工程，输出位于 project_uart/build。

## 7. 分阶段验证和验收

1. UART：验证复位、连续字节、0x00/0xFF、伪起始位和错误停止位；验证 50 MHz 下的 1.5 Mbps 分数计时。使用独立的理想串口激励源和接收监视器，并加入适度波特率偏差，避免收发两端使用同一计时器掩盖错误。
2. 协议：验证完整包、分段输入、坏 CRC、非法长度、截断超时、序号错误、重试和重新 START；确认错误数据不参与处理。
3. 像素处理：用纯色、渐变和边界值校验三种模式，逐像素对照 Python 整数参考结果。
4. 系统仿真：串口位级发送小图，解码 TX 回包并与参考结果比较；覆盖单像素、整块、最后一个短块、处理途中复位和重复包。
5. Vivado：完成 elaboration、综合、资源报告、实现时序和 DRC 检查；检查 RAM 推断及模块结构与方案一致。未执行前不宣称已通过。
6. 上板：以 1.5 Mbps 验证 PING 和小图原图回传，再验证灰度/反色、128×128 和 320×240，并记录实际耗时；若出现错误，使用参数化低波特率帮助定位。保存至少一组原图、参考图和回传结果。

验收条件：原图模式与发送的 RGB565 数据逐字节一致；灰度/反色与参考模型一致；错误包能够拒绝并恢复；图片无缺行、错位或长度不一致；复位后可开始新传输。上板结果需真实硬件验证，本方案不代表已经验证成功。
